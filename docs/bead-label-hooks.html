How the bead-label hooks work

Two files in .claude/scripts/: a shell script that runs on three Claude Code events, and a Python module that the shell script calls for one decision.

Yes, they work together, and only one of them is a hook.

label_bead_on_skill_invocation.sh is the hook. Claude Code runs it. It finds the bead, decides which label a skill earns, and applies the label.

claim_bead_for_build.py is a helper. Nothing but the shell script runs it, and only when the skill is /build. It answers one question: may this session claim the bead?

The parts

shell, about 1,200 lines

label_bead_on_skill_invocation.sh

Runs on PreToolUse (matcher Skill), UserPromptSubmit, and Stop. It needs bd, jq, and git.

Python, about 290 lines

claim_bead_for_build.py

Standard library only, for Python 3.9. It sits beside the shell script, and the shell script runs it with python3. It has its own test suite.

A third file, run_codex_bead_hooks.sh, lives in .codex/scripts/. Codex runs it, and it passes the Codex payload to the same shell script. It is not part of the Claude Code path.

The three events

A hook that fires when a skill starts cannot know how the skill ends. So the work is split: the first two events record what was asked for, and Stop checks what happened.

EventWhen it firesWhat the script does
UserPromptSubmitA prompt starts with /name (or $name in Codex) Maps the command name to a skill, then runs the shared flow
PreToolUse, matcher SkillClaude calls the Skill tool Reads the skill name from the payload, then runs the same shared flow
StopEvery time Claude yields, not only when the work is done Looks at each pending marker and reads that skill's report

Both start events can fire for one run. That is safe: a claim this session already holds reads as "already held", and a marker is written again under the same name.

The label says "this skill ran". That is true the moment it starts, so the script writes the label right away.

The label says "this skill succeeded". The script writes a marker file and waits. Stop reads the skill's report and applies the label only when the report passes.

The script told the model to run bd update --add-label itself. No skill uses it now. It landed fewer than half its labels, because the model often did not act.

The shared flow at the start of a skill

Step 1: finding the bead

A bead id can look like tadw-b14, fathom-3oo.8, or a bare e12, so shape alone cannot tell an id from a word. The script collects candidates and asks bd show about each one. The tracker decides.

  1. Sources: the skill's arguments, the branch name, and a pull request's title, branch, and body when the arguments name one.
  2. Order: segment two of a three-part branch goes first, such as e12 in outrigger/e12/slug. Then come tokens with a hyphen or a dot, longest first, then bare words.
  3. Two cheap filters: a hyphenated candidate must start with a prefix this repository uses. A bare candidate must be six characters or fewer and hold a digit.
  4. Cap: at most 12 candidates, because each one costs a bd show call.

Step 2 in detail: the claim, decided in Python

The shell script already holds the bead's JSON from step 1. It passes the status and the assignee as arguments and the hook payload on stdin:

python3 claim_bead_for_build.py claim <bead-id> <status> <assignee>   # payload on stdin

The module builds this session's actor from the payload's session_id: <git user.name> (session <first 8 characters>). Every window on one machine shares one user.name, so the session part is what tells two windows apart.

A payload with no session_id has no actor. The module then claims as the plain user.name and refuses nothing, because it cannot tell one session from another.

What the module sends back

One JSON object on stdout, plus the exit code:

{"outcome": "claimed in_progress as Jason (session 1a2b3c4d)", "hook_output": { ... }}
FieldWho reads itWhat it holds
outcomeThe shell scriptThe text for the log line, such as claimed in_progress or REFUSED, in_progress under ...
hook_outputClaude Code, by way of the shell script's stdout On a claim: the context line bead-claim: this session holds <id>. On a refusal: a block for UserPromptSubmit, or a deny for PreToolUse

The bead-claim: line matters. /build Phase 1 stops on an in_progress bead unless that line is in its context. Without the module, the shell script logs a failed claim and /build runs with no claim at all.

Gate mode: the marker and the report

A marker is a small file in <git-common-dir>/pending-bead-labels/. Its name carries the label and the bead: implemented__tadw-b14. It has four lines.

1791234567              # when it was written, in seconds
tadw-b14                # the bead
tadw:feature-development   # the skill, which picks the report reader

What each report must show

The script ignores any verdict field in the build and acceptance reports. It reads the counts and works out the answer itself, so a model cannot label its own work by writing "PASS".

ReportPasses only when
build-report.json criteria_total is above 0 and equals criteria_met; tests_passed is above 0; tests_failed is 0; lint_ran is true; lint_violations is 0; and bead names the marker's bead
acceptance-report.json criteria_total is above 0 and equals criteria_passed; criteria_failed and criteria_unverifiable are 0; gates_total is above 0; gates_failed and gates_blocked are 0
quality-gates-report.jsonverdict is exactly PASS
a /qa report0 Critical, 0 High, and 0 Deferred

Each report is read from <git-dir>, so a linked worktree reads its own report. Markers sit in the git common dir, which every worktree shares.

When something goes wrong

Every failure path exits 0, so a skill always runs whether or not its bead could be labeled. The one exception is the /build refusal. Because exit 0 hides a failure, three tools show it:

The log

bead-label.log records each outcome with the hash of the script copy that wrote it. Look for applied, withheld, FAILED, or REFUSED.

--doctor

Run the hook with --doctor. It prints the bead this branch resolves to and what each labeled command would do. It writes nothing.

--check

Run the installer with --check. It says whether each installed copy matches its source and whether all three events are connected.

A stale copy is the usual cause of a missing label. Compare the script= hash in the log with the hash --check prints for the source.
