Eval-Driven Development for Claude Code Skills, Commands, and Agents

A skill is a prompt, and a prompt is an unverified claim about model behavior until you measure it. This is what measuring costs, what it requires, and how to do it in this repository.

1. Why prompts need evals

Every skill, command, and agent in this repo is a document that tries to change what a model does. Nothing about writing one proves it works. A skill can be well written, correctly registered, documented in two places, and still change nothing, because prose is a request and not a mechanism.

There are exactly two ways a prompt artifact fails, and they need different tests:

Failure one

It never loads

The model never invokes the skill, so its content is irrelevant. This repo has shipped it twice. AGENTS.md records style-rspec as "well written, documented, never loaded", with a description scoped so narrowly it could not fire on current work.

Failure two

It loads and does nothing

The document is in context and the output is unchanged. Measured here: a flat ban on the words "green" and "a flake" was violated in 14 of 14 runs across three versions of the same document, including two rewrites aimed at that exact rule.

The core claim

A unit test asserts add(2, 2) == 4. You cannot assert that on a written answer, because a thousand different sentences are all correct. An eval replaces the exact-match assertion with a rule, and replaces certainty with a rate. That is the whole idea. Everything below is bookkeeping around it.

2. Anatomy of an eval

Four parts, and dropping any one of them makes the result unreadable:

PartWhat it isWhat happens without it
Prompt A fixed question that reproduces the situation where the rule applies. You measure the model's mood, not the rule.
Arm The configuration under test. Here: with the plugin loaded against without it. You cannot tell whether the artifact did anything. The model may already behave that way.
Grader The thing that decides pass or fail. A script, or a second model call. You are reading outputs and forming an impression, which is not a measurement.
Runs The same prompt sent more than once. Three to see a pattern, five to decide. One passing run proves nothing. One failing run proves nothing.

The arm is the part people skip

A single-arm run tells you the model produced good output. It does not tell you your document caused it. Modern models write decent tests, lead with the answer, and avoid jargon a fair amount of the time unprompted. Without a baseline arm you will credit your prompt for the model's defaults, and you will keep every useless rule you ever wrote.

3. The three eval types

They differ by roughly an order of magnitude in cost, so pick deliberately rather than defaulting to the expensive one.

Cheapest

Invocation evals

Question: does the artifact load when it should, and stay quiet when it should not?

Grader: deterministic. The skill appears in the session's loaded set, or it does not.

Runs: one per prompt. There is little variance in a binary registry check.

Needs: positive prompts and control prompts, because a skill that fires on everything is also broken.

Middle

Structure evals

Question: does the produced artifact have the required shape?

Grader: deterministic on the document. Sections present, acceptance criteria testable, table drawn or not drawn.

Fits: plan-feature, plan-review, bead-audit, product-brief, and any skill whose output is a document with a specified skeleton.

Most expensive

Behavior evals

Question: does the loaded artifact change the content of the output?

Grader: regex where the rule is lexical, a rubric plus a blind judge where the output is code.

Cost: two arms times three or five runs per case, so a six-case suite is 36 model calls.

Start with invocation evals. They cost about a tenth of a behavior eval and they catch the failure that makes every other measurement moot. A behavior eval on a skill that never loads is a very expensive way to measure the base model.

4. The six requirements

These are the conditions under which an eval result means something. They came out of a real session in this repo, and two of the six are still missing from the harness.

  1. Write the case before the change

    The case defines what "better" means while you can still be honest about it. Write it after and you will write a case your change happens to pass. In the worked example below, the label rule was measured at 0 of 14 before anyone touched it, which is why the later rewrite could not be graded on vibes.

  2. Build a real "before" arm

    Not "I remember it was worse". Check out the released commit into a scratch git worktree and run the same cases against it, concurrently if you can. This repo's runner has no flag for that yet, so it is done by hand: 

    git worktree add /tmp/baseline v2.3.0
env -u ANTHROPIC_API_KEY python3 /tmp/baseline/evals/run.py --case my-case --runs 3 --no-baseline
git worktree remove /tmp/baseline --force

    The runner derives its plugin directory from its own file location, so running the worktree's copy tests the worktree's documents.

  3. Pre-register the bar

    State the number that would change your mind, in writing, before the run. "0 of 5 means prose cannot hold this rule and we move to enforcement." Without it you will reinterpret whatever comes back, and a measurement you can reinterpret is decoration.

  4. Grade deterministically wherever possible

    A regex is free, instant, and gives the same verdict every time. Reach for a model judge only when the property is genuinely not mechanical, such as "is this test suite well structured". When you do, make it blind, score per criterion with cited evidence, and state the blinding limitation rather than claiming it away. A treatment output often identifies itself through its own style.

  5. Keep the raw output

    A failing case you cannot see is a failing case you cannot diagnose. This repo carried an undiagnosed failure in evals/README.md for exactly that reason: the grader reported a missing bold recommendation that a hand-captured response clearly contained, and nobody could inspect what the grader actually received. Always pass --json.

  6. Run more than once

    One run is an anecdote. Three shows a pattern. Five is the minimum for a decision that changes a rule. Sampling error at these sizes is large, so treat a two-run difference as noise and say so out loud.

5. Claude Code specifics

Generic eval advice ignores three things that decide whether a Claude Code eval is even possible.

How the artifact reaches the model differs by type

ArtifactHow it loadsWhat an eval can measure
Hook-injected document
SessionStart		 Injected as raw context into every parent session, with no model decision involved. Behavior only. Invocation is guaranteed, so the arm is plugin loaded against not loaded.
Model-invoked skill The model reads the frontmatter description and decides to call it. Invocation and behavior. The description is a first-class deliverable with its own test.
Skill with disable-model-invocation: true Only a hook or an explicit command can load it. The Skill tool refuses it. Behavior only. An invocation eval here would measure nothing, and a command that tries to invoke it through the Skill tool silently does nothing.
Command /name The user types it. Invocation is deterministic. Behavior, plus whether the command's instructions actually route to the intended skill.
Agent (subagent) Spawned with its own context. It does not inherit the parent session's injected style. Behavior, measured on the agent's returned text. Remember that the response style is deliberately parent-only, so do not grade a subagent against it.

The registry loads at session start

A skill authored in the current session is not invocable until a restart. An invocation battery run in the session that wrote the skill scores zero for a reason that has nothing to do with the skill. This blocked an acceptance criterion in bead tadw-wdk, and the fix is procedural: run invocation evals first thing in a fresh session.

ANTHROPIC_API_KEY breaks the nested call

The harness shells out to claude -p. When ANTHROPIC_API_KEY is set, that call exits 1 with a warning about connectors, every case fails at the invocation check, and the summary still prints a score as though something had been measured. A full six-case run scored 0 of 6 this way; the same tree scored 3 of 6 with the variable unset. Until tadw-evals-strip-api-key-drc lands, prefix every run with env -u ANTHROPIC_API_KEY.

Cost is measured in nested sessions

Each run is a full claude -p invocation with its own context. Cost scales as cases × arms × runs, and wall clock is dominated by model latency, not by your grader. Parallelize across arms, keep --runs 1 for smoke checks, and reserve five-run passes for decisions.

6. The harness in this repo

Everything lives under evals/. It is about 240 lines of Python with no dependencies.

evals/
  run.py                      # the runner: prompts, arms, graders, reporting
  README.md                   # what an eval is, current state, known defects
  cases/
    decision-matrix-suppress/case.json
    decision-matrix-trigger/case.json
    exact-names/case.json
    jargon-tombstone/case.json
    plain-sentences/case.json
    self-report-plainly/case.json

How the arms are built

The with-plugin arm passes --plugin-dir pointed at the repo root, so the SessionStart hook injects the style from your working tree rather than from the released copy in ~/.claude/plugins/cache. The baseline arm passes no plugin at all. The gap between the two is the measurement. 

# with-plugin arm
claude -p "<prompt>" --model sonnet --plugin-dir /path/to/templeton-agentic-dev-workbench

# baseline arm
claude -p "<prompt>" --model sonnet

Running it

# everything, one run per case, both arms
env -u ANTHROPIC_API_KEY python3 evals/run.py

# one case, three runs, plugin arm only, keep the raw output
env -u ANTHROPIC_API_KEY python3 evals/run.py \
  --case self-report-plainly --runs 3 --no-baseline --json /tmp/out.json

# print every answer as it lands
env -u ANTHROPIC_API_KEY python3 evals/run.py --case exact-names --show-output

Flags: --case, --model (default sonnet), --runs (default 1), --no-baseline, --timeout (default 300s), --show-output, --json. Exit status is 0 when every with-plugin run passes, so it can gate a commit.

7. Adding a case

One directory, one case.json. The why field is not decoration: it is where you pre-register what the case is for, so a later reader can tell whether a change to the case was a repair or a retreat. 

{
  "prompt": "A fixed question that reproduces the situation the rule governs.",
  "why": "Which rule this tests, what failure it catches, and why this prompt baits it.",
  "checks": {
    "max_sentence_words": 35,
    "forbid_regex": [
      {"pattern": "\\btombstone\\b", "why": "borrowed metaphor; name the mechanism"}
    ],
    "require_regex": [
      {"pattern": "TADW_STYLE_CORE=off", "why": "technical names stay verbatim"}
    ],
    "forbid_label_alone": [
      {
        "pattern": "\\bflak(e|es|ey|y|iness)\\b",
        "unless_all": ["3,?499", "(again|re-?ran|re-?run|retry)"],
        "why": "the label may summarize the facts, never replace them"
      }
    ],
    "require_markdown_table": true
  }
}

Design the prompt to bait the failure

A good case hands the model the exact situation that produces the bad habit, then forbids it. self-report-plainly gives the model a passing suite plus one test that failed once and then passed, which is precisely the situation that produces "green" and "a flake". A prompt that does not tempt the failure cannot detect it.

8. Grader taxonomy

GraderShapeUse it forStatus
forbid_regexPattern must be absentWords that are wrong in every context: "tombstone", "surfaced", "smoke test"Built
require_regexPattern must be presentFacts the answer must contain: a count, an exact setting nameBuilt
forbid_label_alonePattern allowed only when every unless_all pattern is also presentConclusions that are legitimate beside their evidence and forbidden without itBuilt
require_markdown_table / forbid_markdown_tableStructural presence, checked by looking for a divider rowA rule about when to draw a table and when not toBuilt
max_sentence_wordsCounting, over prose with code and tables strippedLength limitsBuilt
skill_loadedThe named skill appears in the session's loaded setEvery invocation evalTo build
Rubric plus blind judgeN binary criteria, scored per criterion with cited evidence, arms labeled A and B in random orderCode quality, test structure, document qualityDesigned in tadw-geh, not built

A grader may be looser than its rule, on purpose, once

The response style states a 25-word sentence limit; max_sentence_words fails only above 35. That gap is deliberate and documented: a check that can never pass stops being run. The rule keeps the tighter number as the target, and the grader catches runaway sentences. Write the gap down where the grader lives, or the next reader will "fix" one of the two numbers.

9. A worked example, end to end

This is the session that produced this document. It is included because the interesting part is not the passing result, it is the two rule changes that the measurement forced.

The rule under test

The response style banned agents from describing their own work with "green" or "a flake", on the argument that a label hides the claim the reader needs: what failed, what was re-run, and why the change cannot be the cause.

The measurements

ConfigurationRunsResultWhat the outputs showed
2.3.0, flat ban30 of 3"flake" or "flaky" in all three
After the ASD-STE100 rewrite30 of 3Unchanged
After promoting the rule to its own section with a six-part contract3, then 50 of 3, 0 of 5Unchanged again. 14 of 14 runs used a banned word
Same runs, substance checks55 of 5Every run gave the count, the re-run, and the reason

What the data changed

The rule's premise was that the label replaces the argument. In fourteen runs it never did: the model produced the full report and then added the label on top. So the ban was failing answers that already served the reader. The rule was retargeted to never let a label stand alone, and the grader became forbid_label_alone. The label check now passes 5 of 5.

Moving a bar, versus lowering one

These look identical from the outside, so the distinction has to be defended in writing. The bar moved because fourteen measurements showed it was in the wrong place, and the substance checks kept their original strictness. Lowering a bar means widening a grader until an inconvenient rule passes, and it is how a suite stops measuring anything. If you cannot articulate which one you are doing, you are doing the second one.

The failure that was hiding underneath

With the label check passing, the case dropped to 1 of 5 on a different rule: sentence length, at 44, 48, 54, and 64 words against a 35-word ceiling and a 25-word rule. That failure had been there the whole time, masked because the label check failed first. It is filed as tadw-self-report-sentence-length-zxu and left failing rather than graded away.

Two grader defects the same run exposed

Both failed answers that were complete, which makes a score uninformative about the rule it claims to test:

  • require /3499/ failed whenever the model wrote 3,499 with a separator, which happened in three of six runs.
  • The re-run pattern did not match "on retry" or "passed on a retry", which was the phrasing the model chose most often.

A grader that fails compliant output is worse than no grader, because it produces a number that looks like evidence. Check your patterns against real outputs before trusting a red result.

The document was priming its own eval

The skill's pre-send check contained the string 3499, the exact test count the eval prompt uses and the grader requires back. The check was therefore partly measuring recall of the document rather than the rule. The number in the document was changed to decontaminate the case. Grep your prompts for strings that appear in your artifacts.

10. Anti-patterns

Loosening a grader until it passes

The single fastest way to end up with a green suite that measures nothing. Leave a failing case failing and file it.

Deciding on one run

These systems are not deterministic. A one-run result is an anecdote wearing a number.

Teaching to the test

Putting the eval's exact strings into the artifact. The case then measures memory, and it will keep passing after the rule stops working.

No baseline arm

You will credit your document for behavior the model had already.

Holistic judge scoring

"Which suite is better, A or B?" invites the judge to guess the arm. Score per criterion with cited evidence instead.

Reporting a score from a broken run

An invocation failure is not a style failure. If the harness could not call the model, it must refuse to print a score.

11. What to build here

The harness is response-style specific in its layout, but the mechanism is general. Four changes make it serve every artifact in the plugin.

  1. Namespace the cases by artifact

    Move evals/cases/<name>/ to evals/<artifact>/cases/<name>/, so style-python and bead-audit can have suites without colliding. Add --suite next to --case.

  2. Add the skill_loaded grader and an invocation battery

    A case type whose prompt is a realistic user request and whose grader asks whether the named skill was loaded. Positive prompts and control prompts, one run each. This is the cheapest coverage in the building, and it must run in a fresh session.

  3. Teach the runner to build its own baseline

    A --baseline-ref <sha-or-tag> flag that creates a scratch worktree, runs the same cases against it, and removes it afterward. Doing this by hand is the step most likely to be skipped, and it is the step that makes a result trustworthy.

  4. Write raw output to disk by default

    Not behind --json. One directory per run with the prompt, the arm, the answer, and the verdicts. A failure nobody can inspect is why this repo's eval README carried an undiagnosed case instead of a fix.

13. Cost model

Cost is model calls. Everything else is free.

behavior suite   = cases x arms x runs
invocation suite = artifacts x prompts x 1
judge overhead   = graded outputs x judges
ActivityCallsWhen to spend it
Smoke check on one case1 to 2Every time you touch a case or a grader
Full response-style suite, one arm, three runs18Before opening a PR that touches the style
Same suite, both arms36When you need to claim the plugin caused the difference
Five-run decision pass on one case5Only when a result would change a rule
Invocation battery, 30 artifacts, 3 positives and 1 control each120Once, then on any description change
Blind A/B with a judge, 4 fixtures, 3 runs, 2 arms, 1 judge each36Per skill, once it is worth proving

Wall clock is dominated by model latency, so run arms concurrently as separate processes. Two arms of the same three cases were run that way here, and the pair cost little more wall clock than the slower arm alone.
